## Collection and persisted jitter

Only Remote OK is registered. Its windows in the application timezone
America/Montevideo are **02:00–04:00, 10:00–12:00, 18:00–20:00**.
User timezones and subscriptions do not affect collection.

The standard library's random.randrange chooses a second inside the next window,
excluding its end. Initialization may use the remainder of the current window.
After a successful collection, the next window is selected. The result is saved
once in next_run_at; ordinary ticks and restarts do not recalculate it.

The dispatcher selects next_run_at <= now and only publishes tasks. Tasks receive
expected_next_run, so stale queued duplicates skip after the schedule changes.
Failures schedule another attempt one hour later, without immediate retries.
Retries may fall outside regular windows.

The Redis lock `collector:remoteok:lock` uses an ownership token and a 660-second
TTL. Release atomically compares the token through redis-py.
The main async workload is limited to 510 seconds; the entire service call is
limited to 600 seconds. Celery soft/hard limits are 540/600 seconds.

API:

```python
await JobPipeline(save_service).run(jobs)
# CollectionResult(received, new, duplicates, failed)

await CollectionService(sessions, redis, timezone).collect_remoteok(
    expected_next_run=None,
)
```

Collection does not call FilterService, ScoringService or Telegram.
HTTP/JSON errors no longer appear as successful empty responses.

## Celery and Beat

Celery uses UTC; its broker and result backend use the computed REDIS_URL.
Serialization is JSON. Each asyncio.run creates and closes its own async
database engine and Redis client.

| Task name | Trigger |
| --- | --- |
| scheduler.dispatch_collectors | Beat every 15 minutes |
| scheduler.dispatch_digests | Beat every 5 minutes |
| jobs.collect_remoteok | Due state or manual request |
| notifications.send_daily_digest | A specific due user_id |

All four tasks were registered and verified on a live worker.
There are no per-user Beat entries. Polling remains a separate process.
Dispatcher frequency means collection may start about 15 minutes after
next_run_at; digest delivery normally occurs within 5–10 minutes of the
configured time, depending on queue load.

## Digest API and guarantees

```python
await DailyDigestService(sessions, client, entitlements).send(
    user_id, expected_date=None,
)
```

Candidates use NOT EXISTS NotificationORM(user_id, job_id), rather than only a
created_at cutoff. Older unseen jobs and jobs omitted by the previous limit
remain eligible later.

JobORM → JobDTO → existing FilterService → existing ScoringService →
score DESC with stable ID ordering for ties → effective threshold and limit.
Scoring remains unchanged. `default_user_filters(timezone)` preserves the
Python/remote/Worldwide/LATAM/South America/Uruguay profile, excluding US-only
jobs. Filters remain shared; no new filter persistence system was added.

Before the first HTTP request, PostgreSQL commits a digest_runs reservation with
unique (user_id, local_date). This prevents repeated summaries and job cards
during the same day, including concurrent Celery tasks.
Empty digests receive empty status and send nothing.
Nonempty digests send a short top-five summary followed by existing cards through
NotificationService. The card limit excludes the one additional summary message.

Individual notifications retain pending/sent/failed records.
Successful messages are not repeated; ambiguous timeouts do not trigger automatic
retries. Partial success produces partial status; failure produces failed.
An interrupted run may remain pending, which also blocks another attempt that
day. The guarantee is at most one digest attempt per local date, rather than
delivery of every message: Telegram and PostgreSQL do not share a transaction.
Jobs whose individual delivery has not been attempted remain candidates for
another day.

## Preferences, trial and effective settings

New settings in Settings and .env.example:

```dotenv
REDIS_HOST=localhost
REDIS_PORT=6379
REDIS_DB=0
SCHEDULER_TIMEZONE=America/Montevideo
TRIAL_DAYS=7
FREE_DIGEST_TIME=09:00
FREE_MIN_SCORE=70
FREE_MAX_JOBS_PER_DIGEST=10
```

Computed REDIS_URL: redis://localhost:6379/0.
FREE_DIGEST_TIME is validated as a local Python time.
Legacy MIN_NOTIFICATION_SCORE/MAX_NOTIFICATIONS_PER_RUN remain accepted for
compatibility but no longer control collection or digest delivery.

Polling startup and the digest dispatcher bootstrap missing preferences and
seven-day trials for existing users, including the owner.
ON CONFLICT DO NOTHING preserves preferences and never renews an existing trial.

EntitlementService centralizes premium capabilities: custom_digest_time and
custom_min_score. Trial is premium when now < trial_ends_at; an active subscription
is premium when subscription_ends_at is absent or now < subscription_ends_at.
Otherwise, free defaults 09:00 / 70 apply without deleting stored preferences.
Timezone and the stored max_jobs_per_digest are not premium features.

| Example | Stored | Effective |
| --- | --- | --- |
| Active trial | 11:30 / score 42 | 11:30 / 42 |
| Expired trial | 11:30 / score 42 | 09:00 / 70 |
| Active subscription | 11:30 / score 42 | 11:30 / 42 |
| Free Madrid | timezone Europe/Madrid | 09:00 Europe/Madrid |
| Free Uruguay | timezone America/Montevideo | 09:00 America/Montevideo |

Payments, preference commands, additional collectors, LLM and ML were not added.
